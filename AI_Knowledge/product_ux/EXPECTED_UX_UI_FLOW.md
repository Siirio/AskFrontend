## 0. Главная идея Ask

Ask — это приложение, где пользователь не обязан вручную обзванивать компании, писать во все WhatsApp/Telegram и выбирать конкретный SKU как в маркетплейсе. Пользователь пишет человеческий запрос: товар, услуга, бренд, проблему, желаемую дату, примерную цену, район или время. Система помогает превратить этот запрос в понятный flow: поиск, результаты, заявка, ответы, чат, история.

Главный UX-принцип:

**Пользователь спрашивает → Ask показывает подходящие варианты или отправляет запрос → бизнес отвечает → пользователь выбирает лучший вариант или общается в чате.**

Ask не должен ощущаться как тяжелый каталог. Категории, фильтры, карточки, товары, услуги и бизнес-страницы помогают запросу, но не заменяют его.

## 1. Глобальная клиентская навигация

В клиентском мобильном приложении нижняя навигация состоит из трех вкладок:

1. `Поиск`
2. `История`
3. `Профиль`

Отдельных вкладок `Главная`, `Чаты`, `Избранное` на MVP быть не должно.

`Поиск` — это стартовый экран и главный экран продукта. Когда пользователь открывает приложение, он попадает сюда. Если он вводит запрос, эта же вкладка переходит в состояние результатов. Если он нажимает назад из результатов, он возвращается к стартовому состоянию поиска.

`История` объединяет прошлые запросы, активные запросы, снапшоты, заявки на услуги, товарные ответы и чаты. Чат не живет отдельно от контекста. Он всегда связан с поиском, товаром, услугой, записью, компанией или конкретным ответом.

`Профиль` содержит аккаунт пользователя, город, контакты, данные для автозаполнения заявок, настройки уведомлений и privacy.

## 2. Вкладка `Поиск`: стартовое состояние

Когда пользователь открывает приложение, отображается вкладка `Поиск`.

На экране должны быть:

- верхняя зона с логотипом Ask и текущим городом;
- основная поисковая строка;
- переключатель scope: `Товары` / `Услуги`;
- второй уровень категорий, который появляется только как уточнение выбранного scope;
- блоки рядом/рекомендованные рядом, если они не превращают экран в маркетплейс;
- нижняя навигация `Поиск / История / Профиль`.

Категории не должны быть отдельной большой витриной на главной странице. Они являются уточнением поиска.

### Поведение scope `Товары / Услуги`

По умолчанию может быть выбран один scope или состояние `Все`, если команда решит его оставить. Но в интерфейсе пользователь должен ясно понимать, что он ищет: товар или услугу.

Если пользователь нажимает `Товары`, то:

- активным становится scope `Товары`;
- под поиском появляется/обновляется горизонтальный список товарных категорий;
- поисковая строка не очищается;
- будущий поиск получает product intent, если raw query не говорит обратное;
- категории второго уровня сужают поиск, но не заставляют выбрать конкретный SKU.

Если пользователь нажимает `Услуги`, то:

- активным становится scope `Услуги`;
- под поиском появляется/обновляется горизонтальный список service categories;
- поисковая строка не очищается;
- будущий поиск получает service intent;
- категории второго уровня помогают отфильтровать услуги, но не превращают экран в каталог.

Если пользователь переключает scope после введенного запроса, raw query сохраняется. Например, пользователь написал `ремонт телефона сегодня`, затем нажал `Услуги`; запрос не должен исчезнуть, просто меняется интерпретация и выдача.

### Второй уровень категорий

Второй уровень категорий должен быть рядом с поиском, а не отдельной сеткой “Категории” в середине главной.

Пример поведения:

- пользователь нажал `Товары`;
- под scope появляется горизонтальная карусель: `Все`, `Электроника`, `Красота`, `Спорт`, `Авто`, `Дом`, `Детям`, `Одежда`;
- пользователь нажал `Электроника`;
- chip `Электроника` становится активным;
- поиск и рекомендации дальше сужаются до товарной электроники.

Если пользователь нажал `Услуги`, список категорий может быть другим: `Все`, `Красота`, `Ремонт`, `Авто`, `Дом`, `Образование`, `Аренда`.

Категории не должны открывать отдельную самостоятельную страницу без запроса, если это ломает search-first модель.

## 3. Нажатие на поисковую строку

Когда пользователь нажимает на search bar:

- экран переходит в состояние ввода;
- появляется кнопка назад;
- поисковая строка становится активным input;
- сохраняется текущий scope и выбранные категории;
- под input отображаются chips активных уточнений;
- клавиатура открывается;
- нижняя навигация может остаться, если не мешает клавиатуре, или временно скрыться в зависимости от native/PWA поведения.

Если input пустой, показываются recent searches, подсказки или популярные формулировки, но не тяжелый каталог.

Если пользователь вводит текст, raw query сохраняется именно как пользователь написал. Система может распарсить intent, категорию, цену, дату, время и район, но не должна переписывать raw query на внутреннее название товара.

Пример:

`стрижка до 5000 завтра в 18:00`

После парсинга рядом с input появляются chips:

- `Услуги`
- `до 5 000 ₸`
- `завтра`
- `18:00`
- `рядом`, если есть геоконтекст

Если пользователь удаляет chip `18:00`, raw query может остаться как был или быть мягко обновлен в UI, но backend должен понимать, что фильтр времени снят.

## 4. Отправка поиска

Когда пользователь нажимает Enter, кнопку поиска или выбирает подсказку:

- создается search session;
- search session становится current;
- пользователь остается во вкладке `Поиск`;
- экран стартового поиска заменяется экраном результатов;
- вверху остается search bar с raw query;
- ниже видны активные chips;
- ниже отображаются результаты или fallback request block.

Если найдено достаточно live results:

- показывается список товаров или услуг;
- фильтры строятся динамически по найденным результатам;
- сортировка по умолчанию — `по релевантности`, но backend должен формировать ее честно: совпадение запроса, наличие/доступность, актуальность, расстояние, цена, категория.

Если результатов мало или точность плохая:

- показывается CTA: `Не нашли нужное? Создать запрос`;
- пользователь может отправить запрос бизнесам;
- запрос будет жить как active request и появится в истории.

## 5. Search results для товаров

На товарной выдаче каждая карточка товара должна показывать:

- изображение товара или placeholder категории;
- название;
- короткие характеристики, если они известны;
- цену, если она известна;
- компанию/продавца;
- город или расстояние;
- статус наличия;
- быстрый action: `Открыть`, `Уточнить`, `Написать`, `Создать запрос`.

Карточка не должна показывать “в наличии”, если это не подтверждено бизнесом или интеграцией. Если источник неясен, показывать `Уточнить наличие`.

### Нажатие на карточку товара

Если пользователь нажимает на карточку товара:

- открывается product detail;
- сохраняется context source: searchId + resultId + businessId;
- back возвращает к текущей выдаче;
- если пользователь написал бизнесу из detail, чат создается с контекстом этого товара.

### Нажатие `Уточнить наличие`

Если пользователь нажимает `Уточнить наличие`:

- создается product inquiry context;
- если есть конкретный бизнес, открывается чат/заявка к этому бизнесу;
- если бизнесов несколько или нет точного совпадения, предлагается создать общий запрос по товару;
- в истории появляется активность по этому товару.

## 6. Динамические фильтры товаров

Фильтры не должны быть статичными.

После получения результатов frontend/backend формируют фильтры из фактических атрибутов найденных товаров.

Для чековых принтеров могут быть:

- цена;
- наличие;
- бренд;
- ширина печати;
- интерфейсы;
- автоотрезчик;
- расстояние.

Для косметики будут другие фильтры:

- бренд;
- тип продукта;
- объем;
- кожа/назначение;
- цена;
- наличие;
- расстояние.

Если атрибута нет в результатах, фильтр по нему не показывается.

Если пользователь включает фильтр:

- выдача обновляется;
- количество результатов пересчитывается;
- search session остается той же;
- active chips обновляются;
- history/snapshot должны знать, что в момент фиксации были такие фильтры.

## 7. Search results для услуг

На выдаче услуг каждая карточка показывает:

- изображение услуги/бизнеса;
- название услуги;
- бизнес;
- примерную цену или “от”;
- примерную длительность, если известна;
- район/расстояние;
- ближайшие предложенные варианты времени, если можно сформировать;
- CTA `Запросить запись` или `Написать`.

На MVP услуга не должна выглядеть как гарантированное бронирование. Ask не является полноценной календарной системой компании.

Правильный смысл:

**Пользователь выбирает желаемое время → Ask отправляет структурированную заявку → бизнес подтверждает, отклоняет или предлагает другое время.**

### Нажатие на карточку услуги

Если пользователь нажимает на карточку услуги:

- открывается service detail или business page с активной вкладкой `Услуги`;
- контекст входа сохраняется;
- back возвращает в результаты;
- если пользователь нажал `Запросить запись`, открывается flow заявки.

### Нажатие `Запросить запись`

Открывается booking/request screen или bottom sheet, где пользователь видит:

- услугу;
- бизнес;
- цену/цену “от”;
- примерную длительность;
- выбор даты;
- выбор желаемого времени;
- автозаполненные имя и телефон из профиля;
- комментарий;
- кнопку `Отправить заявку на запись`.

После отправки:

- бизнес получает структурированную заявку;
- у клиента появляется активность в истории;
- может открыться чат;
- статус становится `Ожидает подтверждения`.

## 8. Почему Ask не блокирует слоты на MVP

На MVP Ask не должен автоматически считать занятые и свободные окна как полноценная CRM.

Причины:

- у бизнеса может быть несколько мастеров;
- одна услуга может выполняться параллельно несколькими людьми;
- длительность услуги примерная;
- в чате могут договориться на другое время;
- бизнес может вести запись в другой системе;
- компания может принять клиента вне стандартного окна.

Поэтому время в клиентском UI — это желаемое время заявки, а не гарантированная бронь.

Если позже будет отдельная staff/calendar system, можно добавить настоящие слоты, мастеров, занятость и блокировку времени. Но это не MVP.

## 9. Подтверждение записи бизнесом

Когда бизнес получает заявку на услугу:

- он видит клиента;
- услугу;
- желаемую дату;
- желаемое время;
- телефон;
- комментарий;
- кнопку перехода в чат;
- actions: `Подтвердить`, `Отклонить`, `Предложить другое время`.

Если бизнес нажимает `Подтвердить`:

- он должен подтвердить финальную дату и время;
- если финальное время совпадает с желаемым, подтверждает без изменений;
- если договорились в чате о другом времени, бизнес указывает другое финальное время;
- клиент видит статус `Подтверждено`;
- история обновляется;
- чат получает system/message event о подтверждении.

Если бизнес нажимает `Предложить другое время`:

- выбирает/вводит альтернативное время;
- клиент получает сообщение/событие;
- статус становится `Предложено другое время`;
- клиент может принять, отказаться или продолжить чат.

Если бизнес отклоняет:

- статус становится `Отклонено`;
- клиент видит причину, если бизнес ее указал;
- заявка остается в истории клиента до окончания retention window.

## 10. Product detail

Product detail открывается из:

- товарной выдачи;
- истории поиска;
- ответа бизнеса;
- похожих предложений;
- business page.

Product detail должен понимать источник входа.

Если пользователь пришел из live search:

- показываются актуальные данные результата;
- back возвращает в live search results;
- CTA ведет в чат/уточнение с этим бизнесом.

Если пользователь пришел из snapshot/history:

- данные, которые были сохранены как snapshot, должны быть помечены как исторические;
- если есть live updates, их нельзя смешивать без маркировки;
- можно показать `Повторить поиск` или `Уточнить заново`.

Если пользователь пришел из business page:

- detail открывается внутри контекста бизнеса;
- back возвращает на business page;
- чат создается с businessId + productId.

---

## 11. Business page

Business page открывается из:

- карточки товара;
- карточки услуги;
- ответа бизнеса;
- истории;
- чата;
- nearby/recommendation block.

При открытии business page система должна знать context source.

Если пользователь пришел из товара:

- активной может быть вкладка `Товары`;
- нужный товар может быть выделен или открыт;
- CTA связан с product context.

Если пользователь пришел из услуги:

- активной может быть вкладка `Услуги`;
- нужная услуга выделена;
- CTA связан с service/request context.

Если пользователь пришел из nearby block:

- открывается общий профиль бизнеса;
- активная вкладка выбирается по основному типу бизнеса или default.

Business page содержит:

- cover/logo/название;
- краткую информацию;
- контакты/чат;
- вкладки `Товары` и `Услуги`;
- дополнительные секции позже: `О бизнесе`, `Филиалы`, `Фото`.

Рейтинги на MVP можно не показывать публично, если данных мало. Их можно собирать, но не отображать до накопления нормальной базы.

## 12. Чат клиента

Чат всегда открывается как отдельный экран/sub-view.

Чат не является общей вкладкой нижней навигации. Он доступен через:

- историю;
- карточку товара;
- карточку услуги;
- business page;
- ответ бизнеса;
- заявку на запись.

Каждый чат имеет context:

- searchId + businessId;
- searchId + product/resultId + businessId;
- searchId + serviceId + businessId;
- bookingRequestId + businessId;
- productRequestId + businessId.

В header чата показывается:

- название бизнеса;
- контекст: товар, услуга, запись или raw query;
- статус, если важен: ожидает ответа, подтверждено, есть ответ.

Back behavior:

- если чат открыт из истории, back возвращает в историю;
- если из business page, back возвращает на business page;
- если из product detail, back возвращает в product detail;
- если из active request, back возвращает в request feed.

Если в чате появляются новые сообщения:

- счетчик в истории обновляется;
- в строке активности бизнеса обновляется messages count;
- unread count очищается после открытия чата.

---

## 13. История клиента

История клиента — это не просто чаты. Это центр возврата к недавним поискам и действиям.

Вкладка `История` содержит:

- `Активные` или `Все`;
- `Чаты`;
- `История поисков`;
- возможно grouped view по времени.

Каждая строка истории может быть:

- поиском;
- товарным запросом;
- ответом бизнеса;
- заявкой на услугу;
- подтвержденной записью;
- чатом;
- завершенной активностью.

### Нажатие на строку истории

Если пользователь нажимает на search history row:

- открывается snapshot details;
- показывается raw query;
- показываются фильтры на момент поиска;
- показываются связанные товары/услуги;
- показываются связанные чаты;
- показывается срок хранения;
- есть action `Повторить поиск`.

Если пользователь нажимает на chat row:

- открывается чат;
- context header показывает, к чему относится диалог.

Если пользователь нажимает на booking row:

- открывается booking/request detail;
- можно перейти в чат;
- можно повторить заявку, если услуга еще актуальна.

## 14. Current search, snapshot и изменения данных

Каждый поиск проходит жизненный цикл:

- `current` — пользователь сейчас работает с этим поиском;
- `active request` — по нему еще ожидаются ответы;
- `snapshot` — зафиксированное состояние результатов;
- `expired` — история больше не отображается клиенту;
- `deleted` — удалено пользователем или системой.

Клиентская история хранит snapshots ограниченное время, например до 10 дней.

Примерная логика:

- активный товарный запрос живет около 2 часов;
- результаты могут обновляться в течение первого часа;
- после часа фиксируется snapshot текущего состояния;
- если новые ответы пришли после snapshot cutoff, система должна решить продуктово: показывать их как late update или не смешивать с snapshot;
- в любом случае нельзя silently менять исторические факты без маркировки.

Если пользователь ушел в другой поиск:

- предыдущий поиск перестает быть current;
- создается snapshot;
- история обновляется;
- новый поиск становится current.

Если пользователь повторяет поиск из snapshot:

- создается новая search session;
- старый snapshot не перезаписывается;
- новый поиск отображается как отдельная активность.

---

## 15. Что делать, если данные изменились

Если цена, наличие, статус, время или ответ бизнеса изменились после того, как пользователь видел результат, интерфейс должен явно различать:

- что пользователь видел раньше;
- что актуально сейчас;
- что изменилось.

Примеры:

Если товар в snapshot был `120 000 ₸`, а сейчас live price `115 000 ₸`:

- в истории показывать snapshot price как историческую;
- в live detail можно показать актуальную цену отдельно;
- не заменять silently snapshot price.

Если услуга была запрошена на 11:00, а в чате договорились на 10:00:

- заявка хранит requested time 11:00;
- подтверждение хранит final confirmed time 10:00;
- в истории показывается `Запрошено: 11:00`, `Подтверждено: 10:00`.

Если бизнес ответил `Есть`, а потом обновил на `Нет`:

- строка ответа обновляется;
- создается event/update;
- не создается дубликат строки от того же бизнеса;
- клиент видит последнее состояние и, если нужно, историю изменения.

## 16. Товарный запрос

Если пользователь не нашел товар или хочет спросить бизнесы:

- он нажимает `Создать запрос`;
- видит подтверждение запроса;
- может уточнить текст, категорию, район, комментарий;
- нажимает `Отправить запрос`;
- запрос отправляется подходящим бизнесам;
- появляется progress card.

Во время dispatch:

- можно показать короткий loading;
- loading заканчивается после отправки;
- дальше ожидание ответов отображается спокойно, без бесконечного spinner.

После первого ответа бизнеса:

- response feed обновляется;
- строка ответа появляется в active request;
- история получает activity;
- если бизнес написал сообщение, chat row получает unread badge.

Response row compact показывает:

- бизнес;
- статус;
- цену, если есть;
- короткий комментарий;
- расстояние;
- время ответа;
- переход в detail/чат.

Expanded row показывает:

- товар/изображение;
- бизнес;
- цену;
- комментарий;
- адрес/2GIS, если есть координаты;
- `Чат в Ask`;
- внешние контакты, если доступны.

## 17. Ответ бизнеса на товарный запрос

Бизнес получает запрос в своей активности.

Он может ответить:

- `Есть`;
- `Нет`;
- `Нужно уточнение`;
- `Есть аналог`.

Если бизнес отвечает `Есть`:

- может указать цену;
- может написать комментарий;
- может прикрепить/выбрать товар;
- ответ появляется у клиента.

Если `Нужно уточнение`:

- строка ответа получает статус уточнения;
- основной CTA ведет в чат;
- бизнес может задать вопрос.

Если `Есть аналог`:

- можно указать альтернативный товар;
- карточка у клиента должна ясно показывать, что это не точное совпадение.

Один бизнес по одному запросу не должен создавать много дублей. Если он обновляет ответ, обновляется та же строка. Можно разрешить ограниченное количество manual update attempts.

## 18. Бизнес-кабинет: общая модель

Бизнес может продавать товары и услуги одновременно. Поэтому кабинет не должен быть только “записи и бронирования” или только “товары”.

Основные разделы MVP:

- `Активность`;
- `Товары`;
- `Услуги`;
- `Профиль компании`.

В бизнес-сайдбаре на MVP не должно быть лишних разделов без реальной логики. `Чаты`, `Записи`, `Категории`, `Сотрудники`, `Аналитика`, `Отзывы`, `Промо`, `Интеграции` не должны появляться как отдельные основные разделы, пока под них нет полноценной продуктовой логики.

Чат не является отдельным разделом кабинета. Чат открывается из конкретной активности, товара, услуги, заявки или ответа. Запись также не является отдельным типом сущности в таблице активности: на MVP запись — это заявка по услуге, которая может быть подтверждена или отклонена бизнесом.

## 19. Бизнес-кабинет: вкладка `Активность`

Вкладка `Активность` — главный рабочий экран бизнеса. Текущий dashboard-подход в целом правильный: это не тяжелая аналитическая панель, а рабочая таблица/лента, где бизнес быстро видит, что требует реакции.

Над таблицей могут быть компактные tabs со счетчиками:

- `Все`;
- `Ожидают ответа`;
- `В чате`;
- `Подтверждено`;
- `Завершено`;
- `Отменено`.

Большие dashboard-карточки сверху не нужны, если они дублируют tabs. Счетчики внутри tabs достаточно.

### Тип активности

В колонке `Тип` на MVP могут быть только два значения:

- `Товар`;
- `Услуга`.

Не должно быть отдельных типов `Чат` и `Запись`. Чат — это канал общения внутри конкретной активности. Запись — это состояние/результат заявки по услуге, а не отдельный тип объекта.

### Колонки таблицы активности

Таблица активности должна содержать:

- `Тип` — только `Товар` или `Услуга`;
- `Запрос` — вместо старого названия `Объект`;
- `Филиал / адрес` — отдельная колонка, а не подстрока внутри запроса;
- `Клиент` — имя клиента и его контакт под именем;
- `Статус` — состояние согласования/обсуждения;
- `Сообщения` — счетчик сообщений или unread badge, если есть непрочитанные;
- `Обновлено` — `только что`, `28 минут назад`, `1 час назад`, `вчера` и т.п.;
- основной action — `Открыть чат` / `Ответить` / `Открыть`;
- secondary menu через `...` только для вторичных действий.

Колонка `Запрос` показывает название товара, услуги или raw query клиента. Адрес филиала не должен быть вложен под текст запроса: филиал/адрес должен быть отдельным полем, потому что бизнесу важно быстро понимать, к какому месту относится обращение.

Колонка `Клиент` должна показывать не только имя, но и контакт клиента под именем, например телефон. Это нужно, чтобы бизнесу не приходилось открывать деталь только ради базового контакта.

### Статусы активности

Статус в активности не должен быть абстрактным или техническим. Он отвечает на вопрос: “на какой стадии сейчас договоренность с клиентом?”

Для MVP достаточно следующих смысловых статусов:

- `Обсуждается` — бизнес и клиент еще не пришли к финальному подтверждению;
- `Подтверждено` — бизнес подтвердил товар/услугу/время, и клиент это видит;
- `Подтверждение отклонено` — подтверждение отменено или отклонено одной из сторон.

Дополнительные технические состояния вроде `Ожидает ответа`, `В чате`, `Завершено`, `Отменено` могут использоваться как фильтры/tabs или lifecycle states, но они не должны превращать колонку статуса в непонятную смесь системных и продуктовых состояний.

### Подтверждение и отмена подтверждения внутри чата

Обновлять статус подтверждения нужно из контекста чата/активности.

Если бизнес в чате нажимает `Подтвердить`:

- статус активности становится `Подтверждено`;
- клиент видит подтверждение у себя;
- в чате появляется system event о подтверждении;
- история клиента и активность бизнеса обновляются.

Если клиент не хотел, чтобы подтверждение оставалось активным, он может нажать `Отменить подтверждение`. Такая же возможность должна быть у бизнеса.

Если одна из сторон нажимает `Отменить подтверждение`:

- статус становится `Подтверждение отклонено` или возвращается в `Обсуждается`, если стороны продолжают диалог;
- клиент и бизнес видят изменение;
- в чате появляется system event, чтобы изменение не выглядело как silent update.

### Правая панель на активности

На экране `Активность` не нужно держать постоянный right sidebar с деталями выбранной строки. Это лишний шум для MVP.

Правильное поведение:

- таблица/лента остается основным экраном;
- при нажатии `Открыть чат` открывается чат конкретной активности;
- при необходимости деталь можно открыть как отдельный экран, drawer или modal, но не держать постоянную правую панель по умолчанию;
- контекст активности должен сохраняться при открытии чата.

Три точки используются только для вторичных действий: архивировать, скрыть, пометить завершенным, отменить, удалить/скрыть из рабочего списка, пожаловаться. Основное действие должно быть видимым и понятным.

## 20. Бизнес-кабинет: вкладка `Товары`

Раздел `Товары` нужен для управления ассортиментом бизнеса. Текущая визуальная идея таблицы правильная, но продуктовая логика должна быть проще: у товара не должно быть отдельного “статуса” в смысле `Активен / Нужно обновить / Завершено`.

Товарная таблица/список показывает:

- `Товар` — название и цена/краткое описание под ним;
- `Категория`;
- `SKU`, если есть;
- `Источник` или способ подтверждения наличия, если это действительно нужно бизнесу;
- `Связанные ответы`, если применимо;
- действия: `Редактировать`, `Выключить/Включить`, `Удалить`.

Колонку `Статус` для товаров не использовать как обязательную. Вместо этого должна быть понятная action-логика включения/выключения.

### Включение и выключение товара

Включение/выключение товара — foundational логика для ассортимента.

Если бизнес нажал `Выключить`:

- товар остается в кабинете бизнеса;
- товар не показывается клиентам в поиске по этой компании;
- товар не должен попадать в результаты поиска по этой компании, даже если клиент точно запросил его по названию;
- правило действует с момента выключения и до момента обратного включения;
- старые исторические ответы/снапшоты не переписываются silently, но live выдача больше не показывает этот товар как доступный от этой компании.

Если бизнес нажал `Включить`:

- товар снова может попадать в клиентскую выдачу по этой компании;
- будущие поиски учитывают этот товар;
- клиентские результаты должны строиться из актуального включенного ассортимента.

Пример:

Клиент ищет конкретный товар. У многих компаний этот товар может быть. Но если именно эта компания выключила этот товар в своем кабинете, то именно эта компания не должна появляться в выдаче по этому товару.

### Удаление товара

Если бизнес нажал `Удалить`:

- товар удаляется из списка на странице `Товары`;
- товар больше не управляется как активная позиция ассортимента;
- клиентская live выдача не должна показывать этот товар от этой компании;
- исторические активности, где этот товар уже фигурировал, не должны ломаться: они могут хранить snapshot/название, но не должны ссылаться на удаленную live-позицию как на актуальную.

### Редактирование товара

Форма редактирования товара содержит:

- название;
- категорию;
- SKU, если есть;
- цену;
- источник наличия/подтверждения, если используется;
- описание;
- характеристики;
- филиалы, если товар привязан не ко всей компании.

После сохранения изменения применяются к будущей live выдаче. Если цена, описание или наличие поменялись после того, как клиент уже видел товар, история клиента должна различать snapshot и live facts.

## 21. Бизнес-кабинет: вкладка `Услуги`

Раздел `Услуги` нужен для управления услугами компании. Текущая таблица в целом подходит: услуга, категория, цена, длительность, состояние и редактирование.

Услуга содержит:

- название;
- категорию;
- цену или “от”;
- примерную длительность;
- описание;
- график доступности;
- состояние показа: `Активна` или `Не активна`.

Для услуг можно показывать состояние `Активна / Не активна`, потому что оно прямо объясняет, показывается ли услуга клиентам. Но не нужно делать лишние статусы вроде `Пауза`, если по сути это просто выключенная услуга.

### Включение и выключение услуги

На уровне каждой услуги должна быть кнопка `Выключить` или `Включить`.

Не нужно выносить большую кнопку `Включить/Выключить` в верхний угол страницы. Действие должно быть рядом с конкретной услугой, чтобы было понятно, какую услугу бизнес меняет.

Если услуга включена:

- в таблице можно показывать `Активна`;
- кнопка действия — `Выключить`;
- услуга может попадать в клиентский поиск и на страницу бизнеса.

Если услуга выключена:

- в таблице можно показывать `Не активна`;
- кнопка действия — `Включить`;
- услуга не должна попадать в клиентский live search по этой компании;
- старые заявки и история не удаляются, но новые клиенты не должны видеть услугу как доступную.

### Редактирование услуги

Форма редактирования услуги содержит:

- название;
- категорию;
- цену или “от”;
- примерную длительность;
- график;
- описание;
- при необходимости ссылку/дополнительную информацию, если бизнесу нужно указать внешний reference.

Примерная длительность помогает клиенту ориентироваться и помогает системе предлагать желаемые окна, но не является гарантией реального свободного слота.

### График услуги

График услуги не должен быть обычным текстовым полем вроде `Пн-Сб, после подтверждения`, если команда уже делает редактирование серьезнее. Нужен управляемый, но не перегруженный вариант.

Правильная MVP-логика графика:

- бизнес один раз задает шаблон доступности услуги;
- можно выбрать дни недели, например `Пн`, `Вт`, `Ср`, `Пт`, `Сб`;
- можно указать интервалы времени, например `10:00–19:00`;
- можно иметь разные интервалы для разных дней;
- можно указать, что услуга работает только “по подтверждению бизнеса”;
- можно добавить исключения позже, но не заставлять бизнес каждый день вручную заполнять календарь.

Смысл графика на MVP: показать клиенту, когда примерно можно запрашивать услугу, и помочь сформировать заявку. Это не полноценная CRM-занятость мастеров.

В будущем можно добавить:

- живую очередь;
- настоящие свободные слоты;
- сотрудников/мастеров;
- исключения по датам;
- авто-блокировку времени.

Но на MVP услуга остается заявкой на желаемое время, а не гарантированным бронированием.

### Общее редактирование услуг

На странице `Услуги` должна быть возможность массово отредактировать общие параметры для всех или выбранных услуг.

Эта функция может находиться рядом со строкой поиска/фильтром филиалов или чуть ниже, но не должна мешать основной таблице.

Массовое редактирование может применять:

- общий график;
- общий филиал/филиалы;
- общий принцип подтверждения;
- массовое включение/выключение;
- общие параметры показа, если они одинаковые для всех услуг.

Важно: массовое редактирование не должно случайно перетирать уникальные цены, длительность или описания без явного подтверждения. Если бизнес меняет общий график для всех услуг, интерфейс должен показать, что именно будет применено и к каким услугам.

## 22. Бизнес-кабинет: заявки на услуги и чат

Когда клиент отправляет заявку на услугу, бизнес видит ее во вкладке `Активность` как тип `Услуга`.

Строка заявки показывает:

- тип `Услуга`;
- запрос/название услуги;
- филиал или адрес отдельной колонкой;
- клиента и телефон;
- желаемую дату и время, если указаны;
- комментарий, если есть;
- статус согласования;
- счетчик сообщений/unread;
- действие `Открыть чат`.

Actions внутри заявки/чата:

- `Открыть чат`;
- `Подтвердить`;
- `Отклонить подтверждение` / `Отменить подтверждение`;
- `Предложить другое время`, если это нужно для услуги;
- `Завершить`, когда обращение фактически закрыто.

Если бизнес подтверждает:

- он подтверждает финальное время/условия, если это услуга;
- статус становится `Подтверждено`;
- клиент видит подтверждение;
- event появляется в чате;
- активность подсвечивается или фильтруется через tab `Подтверждено`.

Если клиент или бизнес отменяет подтверждение:

- статус меняется на `Подтверждение отклонено` или возвращается в `Обсуждается`, если диалог продолжается;
- обе стороны видят изменение;
- событие фиксируется в чате и истории.

Если бизнес предлагает другое время:

- клиент получает предложение;
- заявка остается активной;
- чат становится основным местом согласования;
- после согласования бизнес может снова нажать `Подтвердить`.

---

## 23. Бизнес-кабинет: профиль компании

Вкладка `Профиль компании` содержит базовые данные бизнеса и не должна превращаться в экран правил/объяснений.

Профиль компании содержит:

- название;
- город;
- телефон для заявок;
- основной филиал;
- другие поля профиля, если они реально нужны бизнесу.

Кнопка `Сохранить профиль` нужна, если форма редактируемая.

Блок `Правила показа` показывать не нужно. Это внутренняя продуктовая логика, а не полезный бизнесу интерфейс на MVP.

Кнопка `Проверить профиль` тоже не нужна на MVP, если за ней нет конкретного рабочего сценария. Не добавлять декоративные кнопки, которые не меняют состояние и не ведут к понятному действию.

---

## 24. Retention: клиент и бизнес

Для клиента:

- история запросов и snapshots живет ограниченное время, например 10 дней;
- это сделано, чтобы клиент мог вернуться к недавним поискам, но история не стала вечным архивом;
- expired история исчезает из обычного UX.

Для бизнеса:

- операционная история не должна удаляться через 10 дней;
- бизнесу нужны данные для учета, аналитики и разбора обращений;
- retention бизнеса должна быть отдельной backend policy;
- бизнес-кабинет может показывать архив и фильтры по датам.

---

## 25. Desktop / PWA клиентская версия

Desktop не должен превращать Ask в тяжелый маркетплейс.

На desktop можно:

- использовать больше ширины;
- показывать карточки в несколько колонок;
- держать фильтры слева или сверху, если это не ломает mobile-first модель;
- но логика остается та же: search-first, не category-first.

После поиска нельзя делать огромный marketplace sidebar категорий, если категории уже были выбраны до/во время поиска. После поиска можно фильтровать найденное: цена, наличие, расстояние, характеристики.

Для услуг на desktop не нужно показывать постоянную правую booking-панель как marketplace. Лучше открывать detail/заявку, чтобы flow был одинаковым с мобильным.

Для бизнес-кабинета desktop-таблица допустима, но постоянный right sidebar на `Активности` не нужен. Основное действие открывает чат/деталь в контексте выбранной строки.

## 26. Empty, loading и error states

Если нет результатов:

- показать raw query;
- предложить убрать фильтры;
- предложить расширить радиус;
- предложить создать запрос.

Если нет бизнесов рядом:

- объяснить спокойно;
- предложить расширить район;
- предложить отправить запрос.

Если сеть упала:

- не очищать input;
- не удалять текущий search session;
- показать retry.

Если запрос отправляется:

- короткий dispatch loading;
- после dispatch loading исчезает;
- ожидание ответов — спокойное состояние.

Если история пустая:

- объяснить, что прошлые запросы появятся после первого поиска;
- action ведет в `Поиск`.

## 27. Non-negotiable flow rules

1. `Поиск` — главный клиентский экран.
2. `Главная` как отдельная нижняя вкладка не нужна.
3. `Чаты` не отдельная нижняя вкладка, а часть истории и контекста.
4. `Избранное` не нужно на MVP.
5. Scope `Товары / Услуги` находится рядом с поиском.
6. Категории второго уровня сужают поиск, а не становятся отдельной витриной.
7. Raw query сохраняется везде.
8. Фильтры после поиска динамические.
9. Рейтинги публично не показывать на MVP, если данных мало.
10. Наличие товара не гарантировать без источника.
11. Услуги на MVP работают как заявка на запись, а не гарантированное бронирование.
12. Бизнес подтверждает финальное время/условия услуги.
13. Чат всегда scoped к конкретному контексту.
14. История клиента хранит snapshots ограниченное время.
15. История бизнеса хранится отдельно и дольше.
16. Business cabinet начинается с `Активности`, а не с перегруженного dashboard.
17. В бизнес-сайдбаре не должно быть лишних разделов без MVP-логики.
18. В активности тип может быть только `Товар` или `Услуга`; `Чат` и `Запись` не являются типами активности.
19. Колонка `Объект` должна называться `Запрос`.
20. Филиал/адрес в активности должен быть отдельной колонкой.
21. Клиентская колонка должна показывать имя и контакт клиента.
22. На `Активности` не держать постоянный right sidebar по умолчанию.
23. Товар не имеет отдельного business-status; товар можно редактировать, удалить, включить или выключить.
24. Выключенный товар не попадает в клиентскую live выдачу по этой компании с момента выключения до обратного включения.
25. Услуга имеет состояние `Активна / Не активна` и действие `Включить / Выключить` на уровне конкретной услуги.
26. График услуги задается как управляемый weekly/interval pattern, а не как ежедневное ручное заполнение календаря.
27. Для услуг нужна возможность массового редактирования общих параметров без случайного перетирания уникальных данных.
28. В профиле компании не показывать блок `Правила показа` и не добавлять кнопку `Проверить профиль` без реального сценария.
29. Обновление ответа бизнеса обновляет ту же строку, не создает дубль.
30. Snapshot и live facts нельзя смешивать без маркировки.

## 28. Формула для Codex

При реализации любого экрана Codex должен сначала ответить на вопросы:

- Откуда пользователь пришел на этот экран?
- Какой context id должен сохраниться?
- Что происходит при back?
- Что меняется в history?
- Что меняется в chat/unread?
- Это live data или snapshot?
- Может ли это измениться после просмотра?
- Если изменится, как UI покажет отличие?
- Это клиентская логика или бизнес-логика?
- Это MVP или future feature?

Если ответов нет, не придумывать маркетплейсную логику, а оставить поведение простым и search-first.
