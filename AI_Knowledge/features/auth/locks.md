LOCKED | Sign-up verifies the email with a 6-digit code (customer/register → verify); log-in is email + password (POST /auth/login, a 2FA challenge runs the shared verify step) | Owner-approved refinement 2026-07-15 (was: OTP for both — see Changelog "Auth refined"; lock amended 2026-07-16 audit); the passwordless OTP login (customer/login/start) and select-role stay deferred with the seller/staff paths | src/auth/api.ts, src/auth/ui/*
LOCKED | The role-choosing modal is triggered by REAL backend data, never by a fabricated intent fork — today that is `purpose === "REGISTER"` on the challenge, OR `suggestRoleExpansion` when it arrives | Product decision 2026-07-15, **amended 2026-07-27 (owner directive)**. The original wording named `suggestRoleExpansion` specifically, and that field turned out to be declared on `AuthSessionResponse` and assigned NOWHERE in the backend — verified across the whole source, not one `.suggestRoleExpansion(...)` call — so the modal PRODUCT_VISION UF 1 step 3 makes unconditional after sign-up could never open, on any account. The lock's intent (a real signal, not an invention) is intact: `purpose` is backend data from the same flow, set from `VerificationPurpose.REGISTER`. Only the field carrying the signal changed, and the dead one is still honoured so nothing breaks when it is populated. Requirement 2 for breaking a lock is met — no surrounding extension existed, because no other populated field distinguishes a fresh sign-up. **Google OAuth is NOT covered**: `/oauth/callback` has no first-signup signal at all, so a Google account still gets no modal — that one is raised with backend, not guessed at (P9.4) | src/auth/ui/RoleSelectionModal.tsx, src/auth/hooks.ts (ROLE_EXPANSION_PURPOSE)
LOCKED | e2e stubs for a backend endpoint are written from the JAVA DTO, never from our own model.ts | Learned the expensive way 2026-07-27: the suite was green for weeks while sign-up 400'd in production, because the stubs answered with `auth_challenge_id` — the name WE used — after the backend had renamed it to `verification_id`. A stub built from the client's assumption can only ever prove the client agrees with itself; it tests nothing about the contract | e2e/*.spec.ts stub bodies
LOCKED | Session state is a zustand store FACTORY consumed via a context provider, never a module-scope singleton | A module-scope store leaks state across SSR requests; the factory+provider is the sanctioned pattern (D7). store.ts stays pure/DOM-free (D5) — side effects live in hooks.ts | src/auth/store.ts, src/auth/hooks.ts, src/auth/ui/AuthProvider.tsx
