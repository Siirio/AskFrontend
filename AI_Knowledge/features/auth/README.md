# Auth & Roles

Mirrors backend module: **identity** (`../Ask_Backend/AI_Knowledge/features/identity/`).

The Authorization Page (sign up / log in) and the session foundation for the whole app. Owns the current user, the role, and the role-choosing modal that follows first entry (PRODUCT_VISION UF 1).

## Key decisions

- **Foundation slice (R6):** any slice may import `@/auth`; `auth/` imports no other slice. The one sanctioned hub — it stays cycle-free.
- **Session state is a zustand store FACTORY consumed via a context provider (D7)** — never a module-scope singleton (which leaks state across SSR requests). `createAuthStore()` (store.ts) holds pure state + actions; `AuthProvider` creates one instance per provider, and the `AuthStoreContext` + `useAuth` hook are DEFINED here and exported via `index.ts` (R6); `app/providers` only mounts `AuthProvider` (R3). Token-storage and API side effects are orchestrated in hooks.ts (`applySessionTo`, `signOut`), keeping store.ts DOM-free (D5). `useAuth` reads via selector subscriptions so consumers re-render only on the fields they select.
- Roles are a **discriminated union** `AuthUser` (customer / business / staff), never one type with optional fields (P4.2). `business` context lives only on the roles that can have it. The kind is derived from the backend `role` string (authority form from verify, bare enum form from GET /session).
- **Every session lands on Home after auth** — `POST_AUTH_PATH` = `/app`, for login, verify and the OAuth callback alike. PRODUCT_VISION UF 1 step 3 states the destination for every role, so there is nothing to resolve per-account; the backend agrees (`resolveStartRoute()` returns the constant `CLIENT_SEARCH`). A seller reaches the cabinet from the nav. **The one flow that lands elsewhere is completing onboarding** → `/app/business` (D26). `startRoute` is modelled but never branched on — see contracts.md, and `locks.md` § Retired for why the old "the backend decides the route" framing was withdrawn 2026-08-01.
- **Sign-up verifies the email with a 6-digit code; log-in is email + password.** Sign-up: `customer/register` → `verify` (code) creates + activates the account. Log-in: `POST /auth/login` (email + password) → a session directly, or a 2FA challenge that runs the shared verify step. The passwordless OTP login (`customer/login/start`) is NOT used in V1.
- **Google OAuth is a REQUIRED second sign-in method on both auth pages (owner directive 2026-07-19).** It reversed the earlier `Email-only auth` lock and was added to PRODUCT_VISION UF 1 the same day, so email+password is no longer sufficient on its own. The button is a full-page nav to `{apiBaseUrl}/oauth2/authorization/google`; the backend writes an `ASK_SESSION` cookie and redirects to the transient `/oauth/callback` page, which **bridges the cookie to a Bearer token** (one credentialed `GET /session` — the decided option-2 hand-off) and then runs the exact `applySessionTo` → `startRoute` path as verify/login. The cookie is only the OAuth bootstrap; the app stays Bearer-only (token lock). Backend **shipped the bridge 2026-07-19**: `/session` exchanges the single-use cookie for the HS256 JWT (+ `expires_in`) and clears it — frontend is fully unblocked, not yet built. See contracts.md + ux-ui-flow.md.
- **The role-choosing modal is persistent and non-dismissable (owner decision 2026-07-17).** After a new customer signs up + verifies, `useVerifyStep` arms a pending flag (localStorage `ask.roleSelectionPending` + the store's copy) and the page navigates to `startRoute`; `RoleSelectionModal`, mounted by the platform layout (EVERY `/app/*` route, auth included — moved from the `(main)` layout 2026-07-18: mounting it only there left an escape via browser-back to `/app/auth/*`), then opens OVER `/app` and stays through navigation and reload until the user answers (card picker + Continue; customer preselected). No close button, ESC and outside clicks are inert. The flag dies with the session (sign-out / token rejected). Modal anatomy follows the owner's reference patterns (see ux-ui-flow). **Answering "customer" also records legal consent** (`POST /legal/registration-acceptances`, `USER_TERMS`+`PRIVACY_POLICY` — built 2026-07-30); "business" does not, since that path only starts seller onboarding (see contracts.md).
- Token storage key is `ask.accessToken`, accessed only through `shared/api` storage helpers (P5.2). Cross-app contract: the marketing landing reads it to redirect logged-in visitors to `/app/` (D6).
- **Route guards — the platform is gated client-side (owner rules 1–2, 2026-07-21; architecture D23).** Two guards are defined here and exported via `index.ts`, mounted by the app composition root (R3): `RequireAuth` (in the `(main)` layout) redirects a logged-out visitor to `/app/auth/login` and gates ALL of `/app/*` except the auth pages — which are reachable logged-out precisely because they sit outside the `(main)` group; `RequireDashboardAccess` (in `business/(cabinet)/layout.tsx` — moved there by D26 so seller registration sits outside it) redirects a customer-only session away from `/app/business` to `/app/business/register` (changed 2026-07-28 from `/app`, so the bounce lands on the page that actually turns them into a seller instead of Home). Both share ONE predicate, `canAccessDashboard(user)` (`model.ts`, exported via `index.ts`), also used by the nav to show/hide the Dashboard link — so link visibility and route access can never disagree (P6.2). The check is **client-side** because the token is localStorage-only (D5/D6), invisible to the server/middleware; a server guard waits on the Phase-4 cookie migration. While the session restores (status `loading`) the guard shows a spinner (`GuardFallback`) — it NEVER redirects before the restore settles, or it would bounce authenticated users to login on every load. Post-login the backend's `startRoute` decides the landing; there is no captured return-URL (P9.1, YAGNI).
- **Two standalone pages, not a tab switcher:** `LoginPage` (`/app/auth/login`) and `RegisterPage` (`/app/auth/register`), each a client page behind a thin server route (D7), sharing an `AuthShell` (a centered column: logo, heading, language + theme controls, card, cross-link). `/app/auth` redirects to login. **No app nav** — the nav lives in the `(main)` route group's layout and auth sits outside it, so the auth pages render standalone (still under the platform LocaleProvider). The Toaster (sonner host) is mounted in the platform layout (moved from `app/providers` 2026-07-18 so it sits inside the `ask.theme` cookie seed and hydrates dark for an explicit dark preference, D21/D19; toasts are platform feedback — the static landing has none and must not read the cookie). Session behavior: the restore in `AuthProvider` also re-runs on the cross-tab `storage` event (D22), so a sign-out or login in one tab immediately syncs every other open tab.
- **Theme toggle + language switch on the auth chrome** (owner request): the light/dark/system toggle (`shared/ui/theme-toggle`, D17) and the ru/kk/en switch (`shared/ui/language-switcher` on the platform LocaleProvider, D18) are domain-free `shared/ui` controls composed by `AuthShell` — auth owns neither mechanism.
- **The screens are ORANGE NEUMORPHISM (2026-07-27, D25)** — auth is under `/app/*`, so it is inside the platform layout's one `neu-skin` wrapper and inherits the skin by placement, not by opting in. The flow, the contracts and every state are unchanged; see `ux-ui-flow.md` § *Visual skin* for what changed visually and for the two places the skin changed BEHAVIOUR: the verification step is now six OTP cells (`CodeInput`, slice-private, submits on the last digit), and the agreement checkbox is a socket-and-fill built on a still-native input. Two slice-private components joined the D8 "auth is the first consumer" set alongside `PasswordInput` and `OAuthOptions`: `CodeInput` and the agreement checkbox — both take their LOOK from `design-system/neumorphism.css`, so promoting either to `shared/ui` later is a move, not a redesign. The previous skin lived on as `auth/ui/*_old.tsx` until 2026-08-01, when that archive was DELETED (D31, owner directive) — it survives in git history, where a `git revert` restores it working; a file copy would not, since `globals.css` removed the `focus-ring-field` utility it depends on.

## Deferred (backend supports them; not built in slice #1)

- Business-owner self-registration (`business/register`) → seller path, roadmap #7. The modal's "set up your business" button routes to the `/app/business` placeholder until then.
- Staff activation (`change-temporary-password`), email change (`email-change/request+confirm`), password change (`password-change/request+confirm`), 2FA settings (`two-factor/request+confirm`), profile update (`/auth/profile`) — all deferred to the profile slice (#6); `isTwoFactorEnabled` is modelled on the session response for completeness but not exercised yet.
- ~~Nav "sign in" entry point + unauthenticated redirect guards arrive with `search` (#2) / `profile` (#6).~~ **Built early, 2026-07-21 (owner directive, D23):** the redirect guards (`RequireAuth`, `RequireDashboardAccess`) landed ahead of those slices, and the nav's signed-out "sign in" entry was REMOVED (owner rule 4) — the platform is now gated, so the nav only ever renders for a session. The sign-out **action** is still defined here (`useAuth().signOut`) and consumed by the profile card later.
